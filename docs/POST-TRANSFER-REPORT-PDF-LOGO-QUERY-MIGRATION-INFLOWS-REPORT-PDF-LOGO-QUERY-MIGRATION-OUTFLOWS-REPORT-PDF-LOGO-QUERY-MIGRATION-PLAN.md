## E. Target Technical Discovery

### E.1 Entry point and report loading

```text
MENU_FILE = lib/features/financial_reports/financial_reports_screen.dart
MENU_TARGET = const OutflowsReportScreen()

```

`FinancialReportsScreen` exposes one Outflows card that navigates to the
screen. The screen requires an authenticated user with
`canViewFinancialReports`; PDF and CSV actions additionally require
`canExportFinancialReports` and a non-null loaded report.

Initialization currently constructs `FinancialReportService` with
`AppRepositories.financialAccountRepository`, loads all financial accounts
including inactive accounts, and automatically applies filters. `_applyFilters`
calls:

```dart
_service.outflowsReport(
  fromDate: _fromDate,
  toDate: _toDate,
  accountIdFilter: _accountIdFilter,
)
```

The UI supports nullable from/to dates and one nullable financial-account
filter. Reset clears all three filters and expanded breakdown state, then
reloads. These service, repository, session, permission, navigation, and filter
dependencies are not part of the ownership migration.

### E.2 Outflows data semantics

`FinancialReportService.outflowsReport` delegates to `_flowReport` with
`FinancialAccountEntryDirection.outflow`. The current contract must remain:

- default `fromDate` is the first day of the current month;
- default `toDate` is the current time;
- all accounts, including inactive accounts, provide the account-name map;
- an account filter limits statement loading to the exact account;
- date bounds use the existing `_isInRange` behavior;
- only outflow-direction entries remain;
- transfer source types are excluded only when no account filter is selected;
- totals and per-source breakdown sum exact integer qirsh values;
- rows sort by timestamp descending and then entry ID ascending; and
- report creation remains read-only.

No report-data query or financial repository ownership changes in this scope.

### E.3 Current PDF and logo path

There is one production call site for `buildOutflowsReport` and one Outflows PDF
trigger. Its current sequence is:

```text
if (_report == null) return
→ AppRepositories.businessIdentityRepository.loadIdentity()
→ Uint8List? logoBytes
→ identity.hasLogo && identity.logo != null
→ AppRepositories.businessIdentityRepository.loadLogoBytes(
    identity.logo!.managedFileName)
→ derive accountLabel from _accountIdFilter and _accounts
→ FinancialReportPdfBuilder.buildOutflowsReport(
    report: _report!,
    accountLabel: accountLabel,
    businessIdentity: identity,
    logoBytes: logoBytes)
→ _showExportResult(file)
```

The Outflows file has four `AppRepositories.` references: report-service
construction, account loading, business-identity loading, and managed-logo-byte
loading. Only the fourth reference is selected. The first three remain, so the
screen remains a locator consumer.

`FinancialReportPdfBuilder.buildOutflowsReport` already accepts the complete
desired data contract: `FlowReport`, nullable `accountLabel`,
`BusinessIdentity`, and nullable resolved `Uint8List` logo bytes. It delegates
to `_buildFlowReport`, preserves the Outflows title and filename, builds an A4
RTL Arabic PDF, and passes identity and bytes to `PdfBrandingHeader.build`.

The branding fallback is already explicit: it renders an image only when
`logoBytes != null && logoBytes.isNotEmpty`, always renders
`businessIdentity.displayName`, and therefore preserves identity-only branding
when metadata is absent or resolved bytes are null/empty. The builder does not
query persistence and requires no change.

The current PDF catch retains the mounted guard, red snackbar, and safe Arabic
`تعذر إنشاء ملف PDF.` message. PDF creation, file naming, output-directory
creation, byte writes, and `_showExportResult` are downstream of the selected
edge and remain unchanged. CSV uses the separate
`FinancialReportCsvExporter.exportOutflowsReport(report: _report!)` path and is
not involved.
